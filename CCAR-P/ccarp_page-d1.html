1.1비즈니스 문제를 솔루션으로 Translating business problems

모든 아키텍처는 기술 선택이 아니라 문제 정의에서 시작합니다. 주니어 아키텍트가 자주 하는 실수는 잘 만든 프롬프트 하나면 될 일에 에이전트를 쓰거나, 컨텍스트 엔지니어링을 개선하면 될 일에 파인튜닝을 쓰는 것입니다. 원하는 결과에서 거꾸로 따라가며 아래 질문에 답한 뒤에야 패턴을 고릅니다.

1.2엔드투엔드 아키텍처 input → processing → output → feedback

단순하든 복잡하든 모든 프로덕션 Claude 시스템은 네 단계로 설명할 수 있습니다. 이 루프를 그리고 설명하는 능력이 가장 자주 출제되는 아키텍처 역량 중 하나입니다.

도면 2 · 4단계 루프

입력 Input

데이터가 어떻게 들어오나? 사용자 메시지, 웹훅, 예약 배치, 문서 업로드. Claude에 닿기 전 정규화와 PII 처리는 무엇을 하나?

처리 Processing

핵심 추론 계층. 모델 호출, 검색, 도구·에이전트 오케스트레이션, 생성 전후에 적용하는 가드레일과 안전 점검.

출력 Output

결과 전달 방식. 사용자 화면, DB 기록, 후속 동작(이메일 발송, 환불, 티켓 업데이트). 생성과 실행 사이에 사람 승인 게이트가 있는가?

피드백 루프 Feedback loop

잘 동작했는지 아는 방법. 명시적 평점, 암묵적 신호(사람이 초안을 많이 고쳤나?), 평가 트레이스, 에스컬레이션·오버라이드 기록. 이 신호가 프롬프트·검색·평가 개선으로 돌아갑니다.

출력에서 끝나면 불완전

피드백 장치 없이 '출력'에서 멈춘 설계는 이 시험 기준으로 미완성입니다. Domain 4(평가)와 Domain 6(라이프사이클 관리)은 피드백 루프가 첫날부터 존재하고 계측된다고 가정합니다. 나중에 덧붙이는 것이 아닙니다.

1.3아키텍처 패턴 augmented LLM · workflow · agent

Anthropic의 "Building Effective Agents" 가이드가 정한 용어를 정확히 써야 합니다. 핵심 구분은 이렇습니다. 워크플로는 내가 작성한 코드가 LLM 호출들을 조율하고, 에이전트는 LLM이 루프 안에서 다음 단계와 도구 호출을 스스로 결정합니다.

도면 3 · 복잡도 사다리 (필요할 때만 한 칸씩)

증강 LLM The augmented LLM · 기본 구성 블록

검색, 도구, 메모리로 보강한 Claude 호출 한 번. 지원 매크로 생성기, 문서 요약기, 분류 단계 같은 대부분의 프로덕션 사례는 이 이상이 필요 없습니다. 오케스트레이션을 더하기 전에 좋은 인컨텍스트 예시를 곁들인 증강 LLM 호출로 이미 해결되는지 먼저 물어보세요.

워크플로 패턴 Workflow patterns · 미리 정의된 코드 경로

프롬프트 체이닝 Prompt chaining

작업을 고정된 순서의 LLM 호출로 나눕니다. 각 단계는 이전 단계 출력을 처리하고, 단계 사이에 코드로 된 '게이트' 점검을 둘 수 있습니다.

적합: 깔끔하고 예측 가능하게 나뉘는 작업. 예) 개요 작성 → 기준에 맞는지 검증 → 전체 문서 작성

라우팅 Routing

입력을 먼저 분류한 뒤, 그에 특화된 하위 프롬프트나 모델로 보냅니다.

적합: 서로 다른 프롬프트나 모델 크기로 처리하는 게 나은 뚜렷한 입력 범주. 예) 단순 FAQ는 Haiku로, 복잡한 에스컬레이션은 Sonnet이나 Opus로

병렬화 · 분할 Parallelization (sectioning)

독립적인 작업을 병렬 하위 작업으로 나누고, 결과는 코드로 합칩니다.

적합: 본 응답과 나란히 도는 가드레일 점검, 여러 측면 평가, 독립적인 문서 섹션

병렬화 · 투표 Parallelization (voting)

같은 작업을 여러 번 돌려 다양한 출력을 얻고, 다수결이나 임계값으로 합칩니다.

적합: 독립 프롬프트 여러 개로 하는 코드 취약점 리뷰, 오탐과 미탐의 균형이 필요한 콘텐츠 모더레이션

오케스트레이터-워커 Orchestrator-workers

중앙 LLM 호출이 작업을 실행 중에 나눠 워커 호출에 위임하고 결과를 종합합니다. 점선은 미리 알 수 없는 하위 작업입니다.

적합: 하위 작업을 미리 예측할 수 없는 작업. 여러 파일에 걸친 코드 변경, 열린 형태의 리서치와 종합

평가자-최적화자 Evaluator-optimizer

한 호출이 생성하고, 다른 호출이 평가·비평합니다. 기준을 충족할 때까지 반복합니다.

적합: 평가 기준이 명확하고 반복 개선의 효과가 분명한 작업. 문학 번역, 여러 차례 검색 후 종합

에이전트 Agents · 모델이 제어 흐름을 결정

에이전트는 계획을 세우고, 환경 피드백(도구 결과, 코드 실행 출력)을 보며 도구를 호출하고, 루프 안에서 다음 단계를 스스로 정하는 LLM입니다. 보통 중단 조건(작업 완료, 최대 반복 횟수, 사람 체크포인트)에 닿을 때까지 돕니다.

도면 4 · 에이전트 루프
지연 증가토큰 비용 증가여러 턴에 걸친 오류 누적

에이전트는 단계 수를 미리 알 수 없는 열린 문제, 그리고 범위가 제한되고 모니터링되는 환경에서 모델의 판단을 믿을 수 있을 때 적합합니다. 위의 비용 때문에 Domain 4(평가)와 Domain 5(가드레일)가 존재합니다.

시험 휴리스틱 · 워크플로 vs 에이전트
→ 워크플로코드를 쓰기 전에 화이트보드에 의사결정 트리를 그릴 수 있다.
→ 에이전트단계의 수와 성격이 모델이 진행 중에 발견하는 것에 따라 정말로 달라진다.

시나리오가 고정되고 감사 가능한 순서를 설명한다면, '에이전트' 보기가 더 그럴듯해 보여도 보통 워크플로가 정답입니다. 그럴듯함은 함정이지 설계 목표가 아닙니다.

1.4멀티 에이전트와 오케스트레이션 Multi-agent systems

한 에이전트의 컨텍스트가 너무 커지거나, 정말로 독립적인 전문 영역이 필요할 때 멀티 에이전트 설계가 등장합니다. 대표적인 형태는 두 가지입니다.

오케스트레이터(리드) + 서브에이전트 Orchestrator + subagents

리드가 목표를 나누고, 도구와 컨텍스트 창 범위를 좁게 정한 서브에이전트에 보낸 뒤 결과를 종합합니다. 각 서브에이전트의 컨텍스트가 깨끗하게 유지되고 병렬 실행이 가능합니다.

대가: 조율 오버헤드. 원본 컨텍스트를 통째로 넘기지 말고 간결하고 구조화된 handoff를 넘겨야 함

P2P · 에이전트 간 통신 Peer-to-peer / agent-to-agent

서로 다른 팀이나 조직이 소유할 수 있는 독립 에이전트들이 공유 오케스트레이터 없이 정의된 프로토콜로 소통합니다.

적합: 에이전트가 신뢰 경계나 조직 경계를 넘나들 때
멀티 에이전트의 실제 비용
서브에이전트 호출마다 별도 과금서브에이전트 멈춤서브에이전트 출력 충돌재귀 위임 폭주

한 에이전트의 컨텍스트나 도구 범위가 정말로 감당 불가능해질 때만 멀티 에이전트를 정당화하세요. 그렇지 않으면 도구를 잘 갖춘 단일 에이전트나 워크플로가 더 안정적이고 저렴합니다.

1.5복잡한 문제의 분해 기법 Decomposition techniques

분해는 비용, 지연, 신뢰성을 동시에 제어하는 아키텍트의 핵심 레버입니다.

기능 분해 Functional decomposition

기능별로 나눠(검색 → 추론 → 형식화) 각 단계가 충족 가능한 가장 저렴한 모델과 가장 단순한 프롬프트를 쓰게 합니다.

데이터 분해 Data decomposition

긴 문서나 큰 데이터셋을 독립 처리 가능한 조각으로 나눈 뒤 합칩니다. 지연을 내주고 병렬성을 얻으며, 컨텍스트 창 한계와 컨텍스트 열화(context rot)를 피합니다.

신뢰도 기반 에스컬레이션 Confidence-gated escalation

빠르고 저렴한 경로를 먼저 시도하고, 신뢰도가 낮거나 위험이 클 때만 더 큰 모델이나 사람 검토로 올립니다.

체크포인트 Checkpointing

LLM 단계 사이에 결정적인 코드 기반 검증 게이트(스키마 검증, 업무 규칙 검사)를 넣어, 오류가 다음 단계로 번지기 전에 잡습니다.

1.6비즈니스 가치 축에 맞추기 Business value pillars

시험은 아키텍트가 설계를 기술 용어뿐 아니라 비즈니스 용어로 정당화하기를 기대합니다. 모든 설계 결정을 아래 축 중 하나 이상에 연결하는 연습을 하세요.

효율 Efficiency

같은 일을 더 적은 사람 시간이나 비용으로평균 처리 시간 감소, 티켓 물량당 필요 인력(FTE) 감소

혁신 Transformation

이전엔 불가능하거나 경제성이 없던 일을 가능하게새 제품 기능, 예전엔 수지가 안 맞던 대규모 개인화

생산성 Productivity

기존 인력의 산출을 증폭Claude Code로 주당 더 많은 PR을 내는 엔지니어, 더 많은 계정을 맡는 분석가

비용 Cost

시스템 운영에 드는 추론, 인프라, 인력 직접 비용요청당 비용, 해결 티켓당 비용, 사람만 쓰는 기준선 대비 총소유비용

성능 SLA Performance SLAs

핵심 정리 Key takeaways · Domain 1

  • 가장 멋진 패턴이 아니라 비즈니스 문제와 요구되는 결정 품질, 지연, 처리량에서 시작한다.
  • 증강 LLM → 워크플로 → 에이전트로 이어지는 복잡도 사다리를 알고, 어디서 멈출지 안다.
  • 모든 아키텍처에는 입력, 처리, 출력, 피드백 루프 네 단계가 모두 필요하다. 피드백이 빠진 설계는 미완성이다.
  • 멀티 에이전트는 비용과 조율 위험을 더한다. 단일 에이전트의 범위가 정말로 감당 불가능할 때만 정당화한다.
  • 각 설계 선택이 어떤 비즈니스 가치 축(효율, 혁신, 생산성, 비용, SLA)에 기여하는지 말할 수 있어야 한다.
