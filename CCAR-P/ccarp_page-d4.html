4.1평가 지표 정의 Defining evaluation metrics

"좋은가?"는 지표가 아닙니다. 운영 수준의 평가 계획은 사용 사례마다 최소 다섯 가지 차원에서 구체적이고 측정 가능한 목표를 정합니다.

도면 1 · 평가의 다섯 차원

정확도 / 품질 Accuracy / quality

정답 데이터에 대한 완전 일치 또는 등급 평가, 작업 완료율, 근거성(모든 주장이 검색된 출처로 추적되는가).지표: 정답률 · 완료율 · groundedness

지연 시간 Latency

SLA에 맞춰 첫 토큰까지의 시간과 완료까지의 시간을 P50/P95/P99로 본다.지표: P50 · P95 · P99

비용 Cost

요청당 비용, 해결한 작업당 비용, 월 추론 총지출과 예산 비교.지표: $/요청 · $/해결 · 월 지출

안전 Safety

유해, 편향, 정책 위반 출력 비율. 가드레일이 발동하는 비율과 잘못 발동하는 비율.지표: 위반율 · 가드레일 오탐율

보안 Security

레드팀에서 프롬프트 인젝션·탈옥 시도가 성공하지 못하고 걸러진 비율, 무단 데이터 접근 시도 차단율.지표: 인젝션 차단율 · 무단 접근 차단율
먼저 정할 것

지표마다 목표(target)와 하한선(floor)을 만들기 전에 정합니다. 그렇지 않으면 "더 좋다"의 기준이 없어서 이해관계자마다 서로 다른 암묵적 기준으로 다툽니다.

알아야 할 정량 지표 Quantitative metrics

분류·추출 작업에서는 정보 검색의 기본 네 지표를 알아야 합니다. 불균형 데이터에서는 정확도만으로는 오해하기 쉽기 때문입니다.

도면 2 · 정밀도와 재현율, 하나로 합치기

정밀도 Precision

시스템이 표시·반환한 항목 중 맞은 비율. 높으면 거짓 양성이 적다.맞은 것 ÷ 반환한 것

재현율 Recall

잡아야 했던 항목 중 실제로 잡은 비율. 높으면 거짓 음성이 적다.잡은 것 ÷ 잡아야 했던 것

F1 F1

정밀도와 재현율의 조화평균. 둘의 균형을 숫자 하나로 볼 때 쓴다.단일 균형 지표

정확도 Accuracy

전체 예측 중 맞은 비율. 클래스가 불균형하면 믿을 수 없다. "항상 사기 아님"이라 답하는 모델은 사기가 1%인 데이터에서 정확도 99%지만 쓸모가 없다.불균형 데이터에서 주의

RAG 검색 품질 RAG retrieval quality

RAG는 검색 단계와 생성 단계를 따로 평가합니다. 검색은 precision@k / recall@k(상위 k개에 맞는 청크가 있는가), 생성은 근거성·충실도(답이 검색된 청크에서 나왔고 지어낸 내용이 없는가), 그리고 답변 관련성(질문에 답하는가)으로 봅니다.

4.2평가 데이터셋과 혼합 방법론 Evaluation datasets and mixed-methodology test frameworks

평가 기법 하나만으로는 충분하지 않습니다. 최소 다음 세 가지를 함께 씁니다.

도면 5 · 세 방법을 합쳐 통과 여부 판단

골든셋 평가 Golden-set exact/graded

대표 입력과 정답(또는 전문가 채점 결과) 모음을 변경마다 자동 실행합니다. 흔한 사례와 알려진 어려운 경계 사례를 모두 넣습니다.

모델 채점 LLM-as-judge

별도의 Claude 호출이 루브릭으로 열린 형태의 출력을 채점합니다. 사람이 못 하는 규모로 미묘한 품질 회귀를 잡습니다. 단, 편향이나 드리프트가 없는지 사람 판단과 주기적으로 검증해야 합니다.

사람 평가 Human evaluation

주관적 품질, 어조, 자동 채점이 놓치는 경계 사례에 필수입니다. 보통 모든 출력이 아니라 표본 추출로 적용합니다.

데이터셋 원칙

데이터셋은 가능하면 실제 운영 트래픽에서 만들고(합성 예시만으로는 부족), 제품과 코퍼스가 변하면 갱신합니다. 정상 경로뿐 아니라 모호한 질문, 범위 밖 요청, 과거 실패 사례 같은 적대적·경계 사례도 명시적으로 포함합니다.

4.3A/B 테스트와 반복 개선 A/B testing and iterative improvement

프롬프트, 모델, 검색 변경을 트래픽 100%에 내보내기 전에 통제된 비교를 합니다.

도면 6 · 측정하고, 판단하고, 출시 후에도 다시 측정
주 지표변경이 움직이려는 지표. 예) 해결률
가드레일 지표나빠지면 안 되는 지표. 예) 안전 발동률, 지연 시간

트래픽을 나누거나 골든셋을 두 변형에 모두 돌리되, 의미 있는 차이를 잡을 만큼 표본이 커야 합니다. "느낌상 낫다" 같은 작은 정성 비교는 대규모 운영 변경의 근거가 되지 못합니다.

주 지표가 개선되고 가드레일 지표가 후퇴하지 않을 때만 승자를 내보냅니다. 애매하면 느낌으로 정하지 말고 데이터를 더 모읍니다.

4.4시스템 문제 진단 Diagnosing system issues

시험은 실패를 올바른 층에 귀속시키는지 반복해서 묻습니다. 증상에서 원인, 확인 위치 순서로 봅니다.

그럴듯하지만 틀린 답 Retrieval / indexing failure

특히 데이터가 바뀐 직후 자신 있고 그럴듯하지만 사실이 틀린 답. 오래되었거나 깨졌거나 무관한 청크가 검색되고 있다.

확인: 이 쿼리에 실제로 어떤 청크가 검색되었는가?

지시를 무시함 Prompt regression

전에는 따르던 명시적 지시를 무시함. 수정이 무언가를 깨뜨렸거나, 컨텍스트 윈도우·순서 문제로 지시가 묻혔다.

확인: 마지막 정상 버전과 프롬프트를 diff, 지시 위치 점검

출처 없는 사실 Hallucination

추적할 출처가 없는 사실, 이름, 인용을 만들어 냄. 근거 컨텍스트가 부족하거나 없거나, 작업이 모델의 신뢰 가능한 지식 범위를 넘었다.

확인: 검색에서 나왔어야 할 주장인가? 인용·검증 요구 추가

광범위한 품질 저하 Model mismatch

배포 뒤 서로 무관한 많은 작업에서 갑자기 품질이 떨어짐. 모델·버전 교체로 동작이 바뀌었거나, 라우팅 설정 오류로 엉뚱한 티어로 트래픽이 갔다.

확인: 마지막 정상 배포와 현재 배포의 모델 ID·버전 비교

지연 시간 상승 Latency overhead

정확도는 그대로인데 지연 시간만 오름. 검색·도구 호출 오버헤드, 캐시되지 않은 프롬프트, 확장/인프라 병목.

확인: 캐시 적중률 텔레메트리, 도구 호출 시간 분해
시험 포인트

실제 시험에서 가장 흔한 틀린 첫 추측 세 가지는 모델 자체를 탓하는 것(temperature, "가중치가 바뀌었다")입니다. 실제 결함은 검색, 프롬프트 구조, 설정에 있는 경우가 많습니다. 항상 증상이 나타난 시점에 구체적으로 무엇이 바뀌었는지 물으세요.

4.5토큰·지연·비용 최적화 Optimizing token usage, latency, and cost-performance

최적화는 "그냥 싸게"가 아닙니다. 해당 SLA에서 비용·지연·정확도 경계의 가장 좋은 지점을 찾는 일입니다. 수단은 비용이 적게 드는 것부터 씁니다.

컨텍스트 축소 Trim retrieved context

핵심 정리 Key takeaways: Domain 4

  • 만들기 전에 정확도, 지연 시간, 비용, 안전, 보안 전반에서 숫자 목표를 정하세요. 나중이 아닙니다.
  • 골든셋, 모델 채점, 사람 평가를 함께 쓰세요. 하나만으로는 충분하지 않습니다.
  • 전체 출시 전에 변경을 주 지표와 후퇴하지 않는 가드레일 지표로 A/B 테스트하세요.
  • 진단은 "무엇이 바뀌었나?"를 먼저 묻습니다. 갑작스럽고 자신 있는 오답의 가장 흔한 원인은 모델이 아니라 검색·색인 실패입니다.
  • 최적화는 ROI 순서로: 캐싱 → 모델 라우팅 → 컨텍스트 축소 → 배치. 더 큰 모델, 투표, 확장 사고는 평가가 효과를 증명한 곳에만 쓰세요.
