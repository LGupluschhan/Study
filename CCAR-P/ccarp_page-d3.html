3.1도구·에이전트의 기능 과잉 Capability bloat in tool and agent configuration

기능 과잉은 작업에 필요한 것보다 많은 도구, 권한, 범위를 에이전트에 주는 일이다. 해결 원칙은 최소 권한이다. 에이전트는 작업에 꼭 필요한 도구만 가져야 한다.

도면 1 · 과잉이 만드는 세 가지 문제
겹치는 도구 정의 사이에서 헷갈림도구 정의마다 컨텍스트 토큰 소모프롬프트 인젝션 한 번의 파급력 증가
공식 가이드의 예시 문항

읽고 초안만 쓰는 지원 에이전트에서 환불/삭제 도구를 빼면 위험을 모니터링하는 데 그치지 않고 아예 없앤다.

기능 과잉 점검 질문 Practical checks

3.2인증과 인가의 공백 Authentication and authorization gaps

모든 통합에서 두 질문에 답해야 한다. 인증은 호출자가 주장하는 그 사람이 맞는가, 인가는 그 호출자가 이 구체적인 일을 해도 되는가를 묻는다.

도면 3 · 두 질문은 따로 확인한다

과도한 서비스 자격증명 Over-privileged credentials

에이전트나 MCP 서버가 필요한 행동에 맞춘 범위 제한 자격증명 대신 관리자급 API 키·서비스 계정 하나를 쓴다.

사용자 컨텍스트 전달 누락 Missing user-context propagation

백엔드 도구 호출이 요청한 사용자의 실제 권한이 아니라 애플리케이션 자체의 넓은 권한으로 실행된다. 사용자가 접근하면 안 되는 데이터나 행동이 조용히 열린다.

인증이 없거나 약한 엔드포인트 Unauthenticated tool / MCP endpoints

내부 도구를 호출자 확인 없이 노출하고, 네트워크 위치를 신원 대신 믿는다.

행동 경계에서 재인가 없음 No re-authorization at the action boundary

여러 단계의 에이전트 흐름이 시작할 때 한 번만 인증하고, 한참 뒤의 민감한 행동(예: 환불) 직전에는 인가를 다시 확인하지 않는다.

시험 포인트

답은 거의 항상 범위를 좁히고, 민감한 행동에 가장 가까운 곳에서 신원·권한을 확인하는 것이다. 과도한 권한 위에 로깅을 더하는 것은 답이 아니다. 로깅은 탐지 통제이고 예방 통제가 아니다.

3.3정확도와 지연 시간의 트레이드오프 Accuracy-latency trade-offs

모든 통합 결정은 정확도·지연·비용의 경계 위 어딘가에 놓인다. 시험은 선택지를 나열하는 데서 그치지 않고 왜 그 지점을 골랐는지 정당화하기를 요구한다.

도면 4 · 하나의 제약이 다섯 레버를 결정한다

더 큰 모델 Larger model

정확도↑ 어려운 사례에서 추론이 낫고 오류가 적다.비용: 지연과 요청당 $ 증가

더 많은 검색 컨텍스트 (RAG) More retrieved context

정확도↑ 근거가 늘고 환각이 줄지만 어느 지점까지만이다.비용: 토큰 증가, 첫 토큰 지연, 과다 검색 시 context rot

확장/적응형 사고 Extended / adaptive thinking

정확도↑ 다단계 추론이 좋아진다.비용: 출력 토큰 증가, 지연 증가

병렬 호출 (투표·앙상블) Parallel calls

정확도↑ 확신이 높아지고 오탐·미탐이 줄어든다.비용: 비용이 배수로 늘고 조율 지연 추가

추가 가드레일·검증 패스 Guardrail / validation passes

정확도↑ 안전하지 않거나 형식이 깨진 출력이 줄어든다.비용: 왕복 지연 추가
방어 가능한 답의 모양

“검색은 상위 5개 청크로 제한하고 Opus 대신 Sonnet을 쓴다. 제품이 2초 미만 응답을 요구하고, 평가 세트에서 이 코퍼스는 5개 청크를 넘으면 정확도가 더 오르지 않기 때문이다.”SLA(제약) + 선택 + 평가 근거를 함께 말한다.

3.4대규모 관찰 가능성 Observability at scale

손으로 검토하는 몇 개의 대화록은 운영 규모에서 관찰 가능성이 아니다. 아래 다섯 가지를 설계에 넣는다.

도면 5 · 관찰 가능성 루프

구조화 로깅 Structured logging

모든 요청/응답 쌍을 토큰 사용량, 지연, 도구 호출, 가드레일 발동과 함께 기록한다. 운영 사고를 사후에 재구성할 수 있어야 한다.근거: 사고 재구성

표본 기반 사람 검토 Sampling-based human review

통계적으로 의미 있는 비율로, 위험도별 층화한다. 환불 같은 고위험 행동은 100%, 일상 채팅은 1-5% 표본.지표: 층화 표본 비율

자동 품질 신호 Automated quality signals

출시 전만이 아니라 운영 중 계속 돈다. 무참조 평가, 가드레일 발동률, 에스컬레이션률, 사용자 피드백(좋아요/싫어요, 수정률).지표: 지속적 신호

드리프트 감지 Drift detection

품질 신호·지연·비용이 과거 범위를 벗어나면 알린다. 문서 갱신이 RAG 인덱스를 깨는 것 같은 조용한 퇴행이 시끄러운 장애보다 훨씬 흔하다.근거: 조용한 퇴행

캐시·도구 진단 Cache / tool diagnostics

캐시 적중률과 도구 호출 성공/오류율을 부수 지표가 아니라 일급 운영 지표로 추적한다.지표: 적중률, 성공/오류율

3.5RAG 파이프라인: 청킹과 인덱싱 Designing a RAG pipeline: chunking and indexing

검색 증강 생성(RAG)은 모델 내부 지식만 쓰지 않고 특정 코퍼스에 Claude의 답을 근거시킨다. 파이프라인은 다섯 단계이고, 시험은 단계마다 판단력을 묻는다.

도면 6 · RAG 다섯 단계

수집 Ingestion

PDF, 위키, 티켓, 코드를 깨끗한 텍스트로 파싱한다. 제목·표처럼 의미를 담은 구조는 보존한다.

임베딩 Embedding

청크를 의미를 담은 벡터로 바꾼다.

인덱싱 Indexing

벡터를 저장하고, 필터링용 메타데이터(날짜, 문서 유형, 접근 통제 태그)를 함께 넣는다. 인덱스 시점의 접근 통제 메타데이터가 있어야 검색이 사용자의 원본 시스템 권한을 지킨다. 자주 놓치는 보안 공백이다(3.2 참고).

검색 + 생성 Retrieval + generation

질의 시점에 질의를 임베딩하고 가장 관련 있는 top-k 청크를 찾고(대개 재순위), 사용자 질문과 함께 Claude에 넘긴다.

청킹: 크기는 트레이드오프 Chunking

청크 크기
너무 작음: 정답에 필요한 앞뒤 맥락을 잃는다너무 큼: 관련성이 희석되고 검색 뒤 토큰을 낭비한다
도면 7 · 청킹 전략 선택

정책 문서, 계약서, 기술 문서에는 대개 제목·문단·논리 절에서 나누는 의미/구조 청킹이 더 일관되고 자기완결적인 단위를 검색해 준다.

3.6데이터 형태별 검색 전략 Retrieval strategies matched to data shape and query pattern

비정형 산문, 자연어 질문 Dense vector (semantic) search

정책, 위키, 지원 문서 같은 비정형 산문에 자연어로 묻는 경우.

최적 전략: 청킹·임베딩한 텍스트에 대한 밀집 벡터(의미) 검색

정확한 용어가 중요 Keyword / lexical, or hybrid

제품 SKU, 법률 인용, 오류 코드처럼 정확히 일치해야 하는 경우.

최적 전략: 키워드/어휘 검색(BM25 계열) 또는 어휘 + 의미를 섞은 하이브리드

구조화된 관계형 데이터 Direct DB query / text-to-SQL

주문, 거래, 재고처럼 구조화된 데이터.

최적 전략: 산문으로 덤프한 것에 벡터 검색을 하지 말고 직접 DB 질의 / text-to-SQL

다중 홉 질문 Graph / agentic iterative retrieval

여러 문서를 조합하거나 개체 사이 관계를 따라가야 하는 경우.

최적 전략: 한 번의 top-k 대신 그래프 기반 검색 또는 에이전트식 반복 검색(검색 → 추론 → 재검색)

다양한 문서가 있는 대규모 코퍼스 Two-stage retrieval

문서 유형이 다양한 매우 큰 코퍼스.

최적 전략: 2단계 검색: 싸고 넓게 건지는 재현 패스 → 비싸고 정밀하게 좁히는 재순위 패스
반복되는 시험 함정

모든 것에 벡터 검색을 기본으로 쓰는 것. 데이터가 정말 구조화되어 있거나(거래 DB) 정확 일치가 필요하면(부품 번호), 직접 질의나 어휘 검색이 정확도와 비용 양쪽에서 의미 임베딩 검색을 이긴다.

3.7연결 프로토콜 선택 Connection protocols: MCP vs. direct API/CLI vs. agent-to-agent

MCP (Model Context Protocol) Open standard

호환되는 어떤 클라이언트든 도구, 데이터, 프롬프트를 노출하는 어떤 MCP 서버든 연결하게 해 주는 개방형 표준(“AI 애플리케이션의 USB-C”). 표준화되고 재사용 가능한 통합 계층이다.

적합: 기존·서드파티 도구와 데이터 소스 생태계에 맞춤 연결 코드를 최소로 쓰며 연결할 때. 같은 통합을 하나의 맞춤 앱이 아닌 여러 AI 클라이언트에서 쓸 때.

직접 API / CLI 통합 Direct API / CLI

특정 API를 호출하거나 특정 명령줄 도구를 실행하는 맞춤 코드.

적합: 범위가 좁고 성능에 민감한 단일 통합이라 범용 프로토콜의 오버헤드가 정당화되지 않을 때. MCP 서버가 없고 일회성이라 만들 가치가 없을 때.

에이전트 간 프로토콜 Agent-to-agent

공유된 중앙 오케스트레이터 없이, 대개 조직이나 신뢰 경계를 넘어 독립된 에이전트끼리 하는 대등한 통신.

적합: 조직 간 워크플로, 또는 서로 다른 팀·벤더가 소유한 에이전트가 직접 협상하고 작업을 주고받아야 할 때.
스타일이 아니라 아키텍처 결정
MCP표준화 계층을 감수하는 대신 재사용성과 성장하는 생태계를 얻는다.
직접 통합좁고 안정적인 사용 사례에서 단순함과 통제권을 얻는다.
에이전트 간한 쪽이 전체 오케스트레이션을 가질 수도, 가져서도 안 되는 곳에서 탈중앙화를 얻는다.

3.8점진적 탐색 vs. 모놀리식 컨텍스트 Progressive discovery vs. monolithic context strategy

에이전트가 많은 도구, 데이터 소스, Skill에 접근할 수 있을 때 이를 노출하는 반대되는 두 전략이 있다.

모놀리식 컨텍스트 Monolithic context

모든 도구 정의, 참고 문서, 가능한 지침을 매 요청마다 미리 컨텍스트에 올린다. 이해하기 쉽지만 현재 작업과 무관한 기능에 토큰·비용·지연을 쓰고, 비슷한 선택지가 많아 모델이 헷갈릴 가능성도 커진다(3.1).

적합: 도구 수가 적고 안정적일 때

점진적 탐색 Progressive discovery

기능의 작고 상위 수준인 디렉터리(예: 도구 검색 메커니즘, Skill 색인)만 노출하고, 모델이 필요하다고 판단한 도구·Skill·문서의 상세만 필요한 때에 요청하게 한다. 수십~수백 개로 늘어도 상주 컨텍스트가 작고 집중된다.

적합: 도구·Skill 카탈로그가 크거나 늘어날 때
도면 8 · 카탈로그 규모에 따른 선택
시험 휴리스틱

도구 수가 적고 안정적 → 모놀리식도 충분하고 더 단순.
카탈로그가 크거나 늘어남 → 점진적 탐색이 필수. 컨텍스트 비대와 도구 선택 오류를 모두 피하기 위해서다.

핵심 정리 Key takeaways: Domain 3

  • 도구·에이전트 범위의 기본 렌즈는 최소 권한이다. 불필요한 기능은 모니터링하지 말고 제거한다.
  • 인증(누구인가?)과 인가(이 구체적인 일을 해도 되나?)를 따로 확인하고, 민감한 행동에 가장 가까운 곳에서 확인한다.
  • 정확도·지연·비용 트레이드오프는 추상적으로가 아니라 명시된 SLA나 비즈니스 제약에 맞춰 정당화한다.
  • 대규모 관찰 가능성은 구조화 로그, 층화 표본, 지속적 자동 평가, 드리프트 감지다. 대화록 몇 개를 훑는 것이 아니다.
  • 청킹과 검색 전략은 데이터의 실제 형태와 질의 패턴에 맞춘다. 구조화 데이터와 정확 일치 요구는 비용과 정확도에서 벡터 검색을 이기는 경우가 많다.
  • MCP, 직접 API/CLI, 에이전트 간 중에서 재사용성, 생태계, 신뢰 경계 요구에 따라 의도적으로 고른다.
  • 도구·Skill 카탈로그가 커지면 점진적 탐색을 쓴다. 모놀리식 컨텍스트는 카탈로그가 작고 안정적일 때만 효율적이다.
